## 2. Exception / what went wrong

### 2.1 Observed error

When Mind Matters is **not** loaded, the game throws:

```
Exception ticking Gola (at (129, 0, 181)): System.TypeInitializationException: The type initializer for 'MindMattersInterface.MindMattersAPI' threw an exception. ---> System.TypeLoadException: Could not resolve type with token 01000037 from typeref (expected class 'MindMatters.MindMattersMod' in assembly 'MindMatters, Version=1.0.0.0, Culture=neutral, PublicKeyToken=null')
   --- End of inner exception stack trace ---
  at PositiveConnectionsNmSpc.PositiveConnectionsExperienceHandler.HandlePositiveExperience (Verse.Pawn initiator, Verse.Pawn recipient, System.String eventType, System.Single probability, MindMattersInterface.ExperienceValency valency, System.Collections.Generic.HashSet`1[T] tags) [0x00024] in .../PositiveConnectionsExperienceHandler.cs:31
  at PositiveConnectionsNmSpc.InteractionWorker_Compliment.Interacted (...) in .../InteractionWorker_Compliment.cs:100
  ...
```

So: a **Compliment** interaction runs → `HandlePositiveExperience` is called → it calls `MindMattersAPI.NotifyExperience` → the **type initializer** for `MindMattersAPI` runs and tries to resolve `MindMatters.MindMattersMod` → that type is in the MindMatters mod assembly, which is not loaded → **TypeLoadException** → **TypeInitializationException**.

### 2.2 Root cause

- **PositiveConnections** already detects Mind Matters and sets a flag:
  - In `PositiveConnections.cs` (constructor): `IsMindMattersActive = ModsConfig.IsActive("cem.mindmatterspr");`
  - There is no mod setting to “use MindMatters”; the mod is either present or not.
- **That flag is never used before calling the API.**
- **PositiveConnectionsExperienceHandler.HandlePositiveExperience** always calls `MindMattersAPI.NotifyExperience` (twice: recipient and initiator) whenever `Rand.Chance(probability)` succeeds. It does **not** check `PositiveConnections.IsMindMattersActive`.
- The project references **MindMattersInterface.dll** (a separate interface assembly). That DLL’s `MindMattersAPI` type has a static initializer that depends on the **MindMatters** mod assembly. As soon as any code touches `MindMattersAPI` (e.g. calls `NotifyExperience`), the CLR runs that initializer; if MindMatters is not loaded, resolution of `MindMatters.MindMattersMod` fails and the exception is thrown.

So: **we only want to touch `MindMattersAPI` when Mind Matters is active.** The fix is to guard all use of `MindMattersAPI` on `PositiveConnections.IsMindMattersActive`.

### 2.3 What needs to be corrected

1. **In `PositiveConnectionsExperienceHandler.HandlePositiveExperience`**  
   Before calling `MindMattersAPI.NotifyExperience`, check `PositiveConnections.IsMindMattersActive`. If false, skip the NotifyExperience calls (and any logging that is specific to MindMatters). The rest of the method (input validation, random chance) can stay; we simply do not call the API when Mind Matters is not loaded.

2. **No change required at call sites**  
   All interaction workers (Compliment, Gift, GiveComfort, SharedPassion, SkillShare, Storytelling, DiscussIdeoligion, Mediation) call `HandlePositiveExperience` with `MindMattersInterface.ExperienceValency` and similar args. Those types come from MindMattersInterface.dll, which is always referenced; the only dangerous part is invoking `MindMattersAPI`. So a single guard inside `HandlePositiveExperience` is sufficient.

3. **Optional later**  
   Document in more detail how Positive Connections interfaces with MindMattersAPI (see next section) once we have the interface or MindMatters mod in view.

## 3. How Positive Connections interfaces with MindMattersAPI (current picture)

- **Assembly**: PositiveConnections references **MindMattersInterface** (`MindMattersInterface.dll`), via HintPath to `../../MindMattersInterface/Assemblies/MindMattersInterface.dll`.
- **Usage**:
  - **Types used**: `MindMattersInterface.ExperienceValency` (e.g. `Positive`, `Affirming`), and the static class `MindMattersInterface.MindMattersAPI`.
  - **API call**: `MindMattersAPI.NotifyExperience(Pawn pawn, string eventType, ExperienceValency valency, HashSet<string> tags)`.
- **Where it’s called**: Only from `PositiveConnectionsExperienceHandler.HandlePositiveExperience`. All interaction workers go through that handler:
  - Compliment, Gift, GiveComfort, SharedPassion, SkillShare, Storytelling, DiscussIdeoligion, Mediation.
- **When it’s called**: After a positive interaction (e.g. compliment, gift) is resolved, with an event type (e.g. `"Compliment"`, `"ComplimentValidation"`), a probability, and a valency. The handler applies a random chance, then calls `NotifyExperience` for the recipient and for the initiator (with a derived event type and tags).
- **Mod detection**: PositiveConnections sets `IsMindMattersActive` in its constructor using `ModsConfig.IsActive("cem.mindmatterspr")`. This flag is currently **not** used before calling MindMattersAPI; adding that check is the fix for the exception above.

We may later expand this section (e.g. with interface signatures or behaviour when MindMatters is present) after inspecting MindMattersInterface or MindMatters.

## 4. MindMattersInterface: 1.5 copy exposed when running 1.6

**What’s going on:** The Makefile only copies MindMattersInterface.dll into **1.5/Assemblies**. The csproj has `OutDir = 1.6/Assemblies` and the reference has `<Private>false</Private>`, so the build does **not** copy the interface into 1.6/Assemblies. When the mod is deployed or published (Steam), the whole tree (1.5/ and 1.6/) is included. So the **only** MindMattersInterface.dll in the package is the one in **1.5/Assemblies**. When RimWorld 1.6 loads the mod, if it loads assemblies from the whole mod folder (or from both version folders), it can end up loading that 1.5 copy—which may be an older or 1.5-specific build of the interface with different type references (e.g. `MindMatters.DynamicNeedsBitmap`), and that can cause the Debug Actions / reflection TypeLoadException.

**Fix:** Copy MindMattersInterface.dll into **1.6/Assemblies** as well (e.g. in the Makefile `verifyapi` target), so the 1.6 runtime has the correct interface DLL next to PositiveConnections.dll. When building for 1.6, ensure the source `../../MindMattersInterface/Assemblies/` is the 1.6-compatible build of the interface.

## 6. Debug menu and MindMattersInterface

One report mentioned something “debug menu” related still referencing MindMattersInterface.

- **In our code**: We have no debug menu or Dev Mode UI that touches MindMatters. The only “debug” label is “Enable Debugging Logs” in mod settings (EnableLogging); that only controls `Log.Message` calls, not the interface.
- **Where we touch the interface**: `MindMattersAPI` is only used inside `HandlePositiveExperience`, and only inside the `if (Rand.Chance(probability) && PositiveConnections.IsMindMattersActive)` block. So we never call the API when Mind Matters is not active. Using the enum `ExperienceValency` in method parameters does not trigger `MindMattersAPI`’s type initializer; only invoking `MindMattersAPI` does.
- **Possible external cause**: RimWorld’s or another mod’s **debug/dev tools** (e.g. “List types”, “Inspect loaded assemblies”) can reflect over our assembly. That could theoretically force type resolution in a way that touches MindMattersInterface or its dependencies. If the user can provide the **exact menu path** or a **stack trace** for the exception, we can see whether it’s reflection from the game or another mod rather than our code path.

### 6.1 Debug Actions menu / DynamicNeedsBitmap TypeLoadException

When opening the **Debug Actions** menu (Dev Mode → "Debug actions" or similar), the game can throw:

```
Exception filling window for Verse.ImmediateWindow: System.TypeLoadException: Could not resolve type with token 01000017 from typeref (expected class 'MindMatters.DynamicNeedsBitmap' in assembly 'MindMatters, ...')
  at LudeonTK.DebugTabMenu_Actions.InitActions (LudeonTK.DebugActionNode absRoot)
  at LudeonTK.Dialog_Debug.TrySetupNodeGraph ()
  at LudeonTK.Dialog_Debug.SwitchTab (RimWorld.DebugTabMenuDef def)
  ...
  at Verse.DebugWindowsOpener.ToggleDebugActionsMenu ()
  at Verse.DebugWindowsOpener.DrawButtons ()
```

**What's going on:** The Debug Actions menu (LudeonTK) builds its tree by **reflecting over loaded assemblies** and looking for debug-action attributes. While doing that, it touches types that reference **MindMatters.DynamicNeedsBitmap**. That type lives in the MindMatters mod assembly. If MindMatters isn't loaded, the CLR can't resolve it → TypeLoadException.

So this is **not** Positive Connections calling into MindMatters. It's the **game's own debug UI** reflecting over every loaded assembly (including MindMattersInterface, or another mod that references MindMatters). Some type in that process has metadata that refers to `MindMatters.DynamicNeedsBitmap`; as soon as reflection hits it, resolution fails.

**Who's in the chain:** Either **MindMattersInterface.dll** (which we load) has types that reference MindMatters types like DynamicNeedsBitmap, or another mod (e.g. Slippers) that references MindMatters/MindMattersInterface does. Positive Connections doesn't register any debug actions and doesn't reference DynamicNeedsBitmap.

**Practical impact:** The exception can be logged once when the Debug Actions window is filled; menus often still work. Fixing it would require either (1) MindMattersInterface (or the other mod) to avoid referencing MindMatters types in reflected metadata when MindMatters isn't present, or (2) the game's debug menu to tolerate TypeLoadException when scanning assemblies. We can't fix it inside Positive Connections alone.

## 7. TypeLoadException when DIL_GiveGift (or any interaction) runs — release build

**Report:** `System.TypeLoadException: Failure has occurred while loading a type` when pawns attempt DIL_GiveGift. Diagnostic logging shows the interaction resolves to `PositiveConnectionsNmSpc.InteractionWorker_Gift`; the exception is thrown during `Pawn_InteractionsTracker.TryInteractWith` and cascades every tick. Disabling or preventing DIL_GiveGift stops the error.

**Cause:** PositiveConnections.dll has a **compile-time reference** to MindMattersInterface.dll. We **do not ship** MindMattersInterface in the release (so the Steam/archive deploy has no MindMattersInterface.dll). The CLR often loads referenced assemblies **on first use**, not at mod load. So when the first interaction that touches MindMattersInterface runs (e.g. Gift’s `Interacted` → `HandlePositiveExperience` with `MindMattersInterface.ExperienceValency`), the runtime tries to load MindMattersInterface.dll. If it’s missing (or wrong version), we get TypeLoadException / “Failure has occurred while loading a type”. So the guard we added (only call MindMattersAPI when IsMindMattersActive) avoids the **MindMattersAPI type initializer** crash, but we still **reference the assembly** (e.g. the enum in method signatures); that reference triggers load when the code path is JITted.

**Fix options:** (1) **Ship a stub MindMattersInterface.dll** with the release that contains only what we need (e.g. `ExperienceValency` enum, and `MindMattersAPI.NotifyExperience` as a no-op), with **no** reference to MindMatters.MindMattersMod or MindMatters.DynamicNeedsBitmap, so the dependency is satisfied and no type resolution fails. (2) **Remove the compile-time reference** and call the MindMatters API via **reflection** only when `IsMindMattersActive` (e.g. resolve type/method from an assembly loaded by the game when MindMatters mod is present). Then our DLL has no dependency on MindMattersInterface and never triggers loading it when the interface isn’t there.

## 8. DIL_ prefix in Defs and code

**Question:** Is DIL_ the correct prefix for interaction/thought/def names, or a mistake in the XML?

**Answer:** **DIL_ is correct and intentional.** It is used consistently: all InteractionDefs (e.g. `DIL_GiveGift`, `DIL_Compliment`, `DIL_Mediation`), ThoughtDefs (e.g. `DIL_ReceivedGift`, `DIL_ReceivedCompliment`, `DIL_ComfortReceived`), RoomRoleDefs (`DIL_PurposeSpaces_Den`), TaleDefs, and keyed strings (`DIL_StorySubject_1`, …) use the DIL_ prefix. The C# code references these with `ThoughtDef.Named("DIL_ReceivedGift")`, `DefDatabase<RoomRoleDef>.GetNamed("DIL_PurposeSpaces_Den", false)`, etc. No change needed.

## 10. Addendum — Mind Matters ↔ interface, read API, Analysis UI (2026)

This section ties **Positive Connections** work to parallel **MindMatters** direction so both mods stay aligned. It is **roadmap / design** where noted; not all items are shipped in any one release.

### 10.1 Other-pawn on experiences and API surface

- **`RelatedPawnThingId`** on `MindMattersInterface.Experience` stores the optional social “other” (`Thing.thingIDNumber`, or `-1`). It feeds **Peacock pertinence** (cognitive field) via cache bump when that pawn is relevant—not only spatial proximity.
- **`MindMattersAPI.NotifyExperience`** supports a **5-argument** path: `(pawn, eventType, valency, flags, relatedPawnThingId)` plus a convenience overload taking `Pawn? relatedPawn`. Positive Connections can pass the interaction partner when recording experiences so downstream UI and psyche logic see **who** was involved.
- **Reflection note:** Any mod that only **reflects** types must still ship a compatible **MindMattersInterface.dll**; the metadata story in **§6** / **§7** still applies.

### 10.2 Deferred (not a commitment to ship next)

- **“Battery” / other-pawn as attractor** — using stored social edges to bias attention or job choice; needs tuning and opt-in.
- **AOSM-style long memory** — separate from short impression decay; ethics and UX need a pass.
- **Ethics / copy** — how strongly to label inferred mental state as “private” or uncertain; **open decision** before aggressive player-facing claims.

### 10.3 Read API goal (MindMatters + interface)

- **Stable getters** for **stored** experiences: `IMindMattersExperienceComponent.GetPawnExperiences` and **`GetRecentPawnExperiences(pawn, maxCount)`** (newest-first by `Experience.Timestamp`).
- **`MindMattersAPI.GetRecentPawnExperiences`** (when Mind Matters is ready) mirrors that for external mods without referencing the game component type directly.
- Intended consumers: **ThinkTree** conditionals, **Psyche Map / Analysis** summaries, future tooling.

### 10.4 Analysis UI direction (MindMatters)

- **Vanilla mood** remains a **convenience** bar (not the core thesis).
- **Persona:** `GetRestingPersona()`-style label (dominant ± secondary mode string).
- **Trending:** modes / impressions — **TBD** (could be deltas or top-N impressions; not merged into a fake causal story).
- **`n` = 3 recent stored experiences** in the **left panel**: event type, valency, optional **related pawn** label resolved on-map when `RelatedPawnThingId` is set.

### 10.5 Non-goals

- **Combat-optimizer** level of detail for mood/thought.
- **Single “spike causality” line** that merges mode deltas, recent events, and related pawn into one **false “because”**. Prefer **honest correlation**: separate lines (e.g. mode context vs recent stored events vs optional other pawn), or clearly labeled uncertainty.

### 10.6 Open decisions (stop here until chosen)

- **Ethics / tone** for mind-state UI (soft vs hard factual wording).
- **Spike attribution UI:** separate lines vs one narrative; must not imply proven causation.
- **ThinkTree** wiring is **out of band** for this doc: Harmony / think nodes when the design is ready.

## 11. Random social eligibility (1.6.x)

When Hospitality (or similar) widens `TryInteractRandomly` beyond same-faction colonists, PC interaction defs can be rolled for **colony prisoners**, **cryptosleep**, or other invalid pairs. PC does not build that pool; it only weights defs once a pair is chosen.

**Implementation:** `PositiveConnectionsUtility.IsEligibleSocialParticipant`, `IsEligibleForRandomSocial`, and `ShouldSkipRandomSocialInteraction`. All eight `InteractionWorker_*` types use `IsEligibleForRandomSocial` in `RandomSelectionWeight` and `ShouldSkipRandomSocialInteraction` at the start of `Interacted`. Mediation also filters `FindConflictPawn` with `IsEligibleSocialParticipant`.

**Rationale / pipeline:** MindMatters design doc `docs/design/random-social-interaction-eligibility.md` (MindMatters repo).

**Build process (1.5 + 1.6 DLLs):** `docs/build-multiversion.md`.
